# クライアント・面接官向け: AIコードレビューの評価・ガードレール工程説明

この文書は、`review-fix-pipeline` と `claude-review-pdca` の仕組みを、クライアントや面接官に説明するための工程別説明である。

ここで伝えたいことは、単に「AIにレビューさせています」ではない。  
**AIが作ったものを、どこで確認し、どこで止め、どこから人間判断に戻すかを、作業前から設計している**という点である。

---

## まず前提: ここでいう評価とガードレール

### 評価とは

ここでいう **評価** は、点数を付けることだけではない。  
AIが作ったコードや判断を、次の工程へ進めてよいか確認するための仕組み全体を指す。

具体的には、次のような確認を含む。

- 動くか
- 壊していないか
- 依頼範囲からはみ出していないか
- 人間判断が必要な変更を勝手に進めていないか
- 同じ失敗を繰り返していないか

### ガードレールとは

ここでいう **ガードレール** は、AIを使わないための制限ではない。  
AIを安全に使うために、**どこまで自動化し、どこから人間に戻すかを事前に決める境界線**である。

クライアント向けには、次のように説明する。

```text
AIに作業を任せる前に、通してよい変更、確認が必要な変更、止めるべき操作を分けています。
AIの判断だけで危険な作業が進まないよう、テスト結果、変更差分、人間承認を通過条件にしています。
```

---

## 用語の置き換え方針

説明では、内部実装寄りの英語を主語にしない。  
必要な場合だけ、括弧で補足する。

| 内部用語 | 説明時の言い方 |
|---|---|
| findings | レビュー指摘。AIレビューで見つかった問題候補。 |
| severity | 重要度。どれくらい重大な指摘かを表す区分。 |
| repo | リポジトリ。プロジェクトのコード一式。 |
| DB | 保存用データベース。レビュー指摘を蓄積する台帳。 |
| auto-fixable | 自動修正候補。仕様判断なしで小さく直せるもの。 |
| judgment call | 人間判断項目。責任ある判断が必要なもの。 |
| critical finding | 重大指摘。本当に起きるなら影響が大きい指摘。 |
| false positive | 誤検知。実際には問題ではない指摘。 |
| rule promotion | ルール昇格。繰り返し使える指摘をプロジェクトルールにすること。 |
| fresh reviewer | 新しい文脈のレビュー担当。実装理由を知らない状態で見るAI。 |
| loop | 反復処理。同じ流れを条件付きで繰り返すこと。 |

---

## 全体像

この仕組みは、AIコーディングを次の流れで制御している。

```text
1. 作業前に、AIに任せる範囲を分ける
2. 実装前に、過去の失敗を思い出させる
3. AIが実装する
4. 別の文脈のAIがレビューする
5. 指摘を、自動修正・人間確認・停止対象に分ける
6. 重大な指摘は、実際に起きるか確認してから直す
7. 安全な修正だけ適用する
8. 修正後に、別の文脈で再レビューする
9. 誤検知が増えたら止める
10. 結果を保存し、次回の実装前に戻す
11. 繰り返し起きるものだけ、人間承認でルール化する
```

クライアント向けには、次の一言で説明できる。

> AIにコードを書かせるだけではなく、作業前・レビュー時・修正時・次回実装時に確認ポイントを置き、危険な判断は人間に戻す品質管理フローです。

## 工程1. 作業前に、AIに任せる範囲を分ける

### 何を制御しているか

AIがどこまで関与してよいかを、作業前に分ける。  
重要なのは、「AIを使うか使わないか」ではなく、**どの判断を機械的に通し、どの判断をAIに補助させ、どこを人間が決めるか**である。

### どうやって制御しているか

作業を4種類に分け、事故が起きる前に止まる場所を決める。

| 区分 | 判断主体 | AIが実際にやること | 事故前にどう制御するか | 確実性の根拠 |
|---|---|---|---|---|
| 機械的に確認できる作業 | テストや検査コマンド | チェックを実行し、失敗した箇所を要約する。 | 成功・失敗はAIの感想ではなく、コマンド結果で判定する。失敗していれば次工程へ進めない。 | 実行結果で判定するため、AIが「大丈夫そう」と言っても成功扱いにならない。 |
| 小さく安全に直せる作業 | ルール + AI実装 | 読み込み漏れ、名前の打ち間違い、単純な条件漏れなどを小さい差分で直す。修正後に関連チェックを再実行する。 | 修正対象、変更範囲、変更の種類を事前に限定する。対象外の変更、広すぎる差分、チェック失敗があれば止める。 | 差分とチェック結果で確認するため、AIが勝手に大きな設計変更を混ぜても完了扱いにしない。 |
| 判断が必要な変更 | 人間 | 選択肢を2〜3案に整理し、影響範囲、移行コスト、確認すべき観点を説明する。推奨案は出してよい。 | 出力を「提案・比較・リスク・推奨」までに固定し、コード変更へ進めない。採用判断が必要な項目は人間確認待ちにする。 | 決定権を人間側に残すため、AIの提案がそのまま仕様変更として実装されない。 |
| 高リスク操作 | 人間承認またはブロック | 実行前に、対象、影響範囲、戻し方、必要な承認、代替案を説明する。可能なら実変更なしの確認までで止める。 | 秘密情報、外部送信、本番操作、破壊的削除、権限変更を事前にブロック対象として定義する。承認がなければ実行しない。 | 実行前ゲートで止めるため、事故が起きた後の検知ではなく、危険操作そのものを実行前に止められる。 |

### どの水準で制御しているか

- 正誤が機械的に分かるものは、AIの文章ではなく実行結果で判定する
- 小さな修正は、対象ファイル・差分・チェック結果で制御する
- 仕様・権限・セキュリティ・互換性の判断は、提案状態で止め、人間の決定なしに実装へ進めない
- 秘密情報・本番操作・破壊的操作は、事後検知ではなく実行前ゲートで止める

### 説明例

```text
この工程では、AIを使うかどうかではなく、事故前にどのゲートで止めるかを決めています。
テストや検査のように結果が明確なものは、AIの感想ではなく実行結果で判断します。
AIには、チェック実行、ログ要約、小さい修正、修正後の再確認までを任せます。
ただし、対象外ファイルの変更、広すぎる差分、チェック失敗があれば完了扱いにしません。
責任判断が必要な変更は、AIには選択肢整理とリスク説明までを任せ、決定は人間確認に戻します。
```

## 工程2. 実装前に、過去の失敗を思い出させる

### 新しい単語

**再注入** とは、過去のレビュー指摘を、次回の実装前にAIの作業文脈へ戻すこと。  
ただし、すべてを戻すのではなく、今編集するファイルに関係するものだけを戻す。

### 何を制御しているか

AIが同じファイルで同じ種類の失敗を繰り返すことを防ぐ。

### どうやって制御しているか

`claude-review-pdca` が、過去のレビュー指摘を保存用データベースに保存している。  
実装前に、対象ファイルに関係するレビュー指摘だけを取り出してAIに見せる。

取り出す条件は次のようなもの。

- 同じプロジェクトか
- 同じファイルか
- 重要度が十分高いか
- 古すぎないか
- すでに解決済みではないか
- 同じ作業中に重複して出していないか

### どの水準で制御しているか

- 全件を読ませない
- 対象ファイルに関係するものだけ
- 低優先度や古いものは除外
- 解決済みや人間が不要と判断したものは再注入しない

### 説明例

```text
レビュー指摘を一回で捨てず、次に同じファイルを触る前に関連する指摘だけをAIへ戻しています。
全件を戻すとノイズになるので、プロジェクト、ファイル、重要度、鮮度で絞ります。
これにより、AIが同じ失敗を繰り返しにくくしています。
```

## 工程3. AIが実装する

### 何を制御しているか

AIが作業範囲を広げすぎること、過去の注意点を忘れて実装することを制御する。

### どうやって制御しているか

実装時には、次の情報を前提に作業させる。

- 対象ファイル
- 過去のレビュー指摘
- プロジェクトのルール
- 確認に使うコマンド
- 依頼された作業範囲

### どの水準で制御しているか

- 依頼範囲外の大規模な書き換えはしない
- 既存ルールと既存設計に合わせる
- 実装後に確認できる変更単位にする

### 説明例

```text
実装工程では、AIに自由に作らせるのではなく、対象ファイル、過去の指摘、プロジェクトルール、確認方法を渡してから作業させます。
これにより、AIがその場の推測で大きく設計を変えることを避けています。
```

## 工程4. 別の文脈のAIがレビューする

### 新しい単語

**別の文脈** とは、実装したAIとは別の会話・別の状態でレビューさせること。  
同じAIでも、実装理由を知っている状態で自己レビューさせると甘くなりやすいため、レビュー用に文脈を分ける。

**意図優先レビュー** とは、先に「この変更は何をしたかったのか」を推定してから、その意図に対して問題を探すレビュー方法である。

### 何を制御しているか

AIが自分の実装を甘く見ること、または意図を無視して的外れなレビューをすることを制御する。

### どうやって制御しているか

`review-fix-pipeline` のレビュー工程では、まず変更意図を推定し、その意図の範囲で問題を出す。  
レビュー担当は実装担当とは別文脈にする。

### どの水準で制御しているか

- 実装とレビューを同じ文脈で閉じない
- 変更意図を推定してからレビューする
- 「好み」ではなく、意図に対するバグ・安全性・保守性の問題を出す

### 説明例

```text
AIが自分で書いたコードを同じ会話でレビューすると、なぜそう書いたかを知っているため見落としが起きやすいです。
そのため、実装担当とレビュー担当を別文脈に分けています。
さらに、レビューでは最初に変更意図を推定し、その意図に対して本当に問題があるかを確認します。
```

---

## 工程5. 指摘を、自動修正・人間確認・停止対象に分ける

### 新しい単語

**自動修正候補** とは、仕様判断なしで小さく直せる可能性がある指摘である。  
「AIが自信あり」という意味ではなく、「意図を変えずに直せる」という意味で使う。

**人間判断項目** とは、仕様・責任・方針の判断が必要な指摘である。  
たとえば、外部から呼び出される入り口の変更、画面の使い勝手の変更、互換性への影響、セキュリティ方針などが該当する。

### 何を制御しているか

AIが、責任ある設計判断まで勝手に直してしまうことを防ぐ。

### どうやって制御しているか

レビュー結果を次のように分ける。

| 分類 | 例 | 次の処理 |
|---|---|---|
| 自動修正候補 | 明らかな参照ミス、読み込み漏れ、単純な条件漏れ | AIが小さく修正し、確認コマンドを再実行する |
| 人間判断項目 | 仕様変更、画面仕様、セキュリティ方針 | AIは選択肢とリスクを説明し、人間確認へ戻す |
| 停止対象 | 本番影響、データ削除、秘密情報 | ブロックまたは明示承認 |

### どの水準で制御しているか

- 自動修正は局所的で意図を変えないものに限定
- 仕様・権限・セキュリティ判断は人間に戻す
- 高リスク操作はAI判断だけで進めない

### 説明例

```text
レビュー指摘は、AIが直してよいものと、人間に戻すものを分けています。
自動修正候補は「AIが自信あり」ではなく、「仕様判断を含まず小さく直せる」という意味です。
設計やセキュリティ方針のような判断は、AIが提案しても自動適用しません。
```

---

## 工程6. 重大な指摘は、実際に起きるか確認してから直す

### 新しい単語

**重大指摘** とは、本当に起きるなら影響が大きいレビュー指摘である。  
ただし、重大と言われたから必ず正しいわけではない。

**実測確認** とは、実際に小さな再現コードやテストを動かして、指摘された問題が本当に起きるか確認すること。

### 何を制御しているか

AIが「重大」と言った指摘をそのまま信じて、動いているコードを壊すことを防ぐ。

### どうやって制御しているか

重大指摘は、修正前に最小限の再現確認を行う。  
たとえば、小さな確認コードや対象テストを実行して、本当に問題が起きるかを確認する。

### どの水準で制御しているか

- 重大指摘は即修正しない
- 実際に確認できるものは確認してから直す
- 確認できないものは、人間判断または追加調査に戻す

### 説明例

```text
重大指摘ほど、そのまま直すと危険です。
AIが重大だと言っても、まず小さく再現して本当に問題が起きるか確認します。
確認できたものだけ修正し、確認できないものは人間判断に戻します。
```

## 工程7. 安全な修正だけ適用する

### 何を制御しているか

レビュー結果をもとに、AIが過剰修正やついで修正を行うことを防ぐ。

### どうやって制御しているか

修正担当は、自動修正候補だけを修正する。  
人間判断項目や高リスク操作は修正対象から外す。

### どの水準で制御しているか

- 修正対象はレビュー指摘に対応するものだけ
- 既存仕様を変えない
- 関係ない整理や作り替えを混ぜない
- 修正後にテストや簡易確認を行う

### 説明例

```text
修正工程では、レビューで見つかった問題のうち、安全に直せるものだけを適用します。
ついでの整理や仕様変更は混ぜません。
これにより、レビュー修正が新しい不具合を作るリスクを抑えています。
```

---

## 工程8. 修正後に、別の文脈で再レビューする

### 何を制御しているか

修正によって別の不具合が入ったり、最初のレビュー担当と同じ見落としが残ったりすることを防ぐ。

### どうやって制御しているか

修正後、別の新しい文脈のレビュー担当で再レビューする。  
同じレビューの続きではなく、新しい状態で見直す。

### どの水準で制御しているか

- 再レビューは修正後の差分を対象にする
- 繰り返し回数に上限を置く
- 新しい自動修正候補が残っていれば再修正
- そうでなければ完了または人間判断へ回す

### 説明例

```text
修正後は、同じ文脈で「直りました」と判断せず、新しいレビュー文脈で再確認します。
これにより、修正による副作用や、最初のレビュー担当の見落としを拾いやすくしています。
```

---

## 工程9. 誤検知が増えたら止める

### 新しい単語

**誤検知** とは、実際には問題ではないのに、AIが問題として指摘したもの。

### 何を制御しているか

レビューを回しすぎて、AIが実問題ではなくノイズを直し始めることを防ぐ。

### どうやって制御しているか

レビューの反復が進むにつれて誤検知が増えた場合、さらにレビューを続けず停止する。

### どの水準で制御しているか

- レビュー回数には上限を置く
- 誤検知の比率が高くなったら止める
- 「全部指摘が消えるまで回す」ことを目的にしない

### 説明例

```text
AIレビューは回せば回すほど良いわけではありません。
実際の問題を取り切った後は、誤検知が増えて、不要な修正で品質を下げることがあります。
そのため、誤検知が増えたら、追加レビューより停止を優先します。
```

---

## 工程10. 結果を保存し、次回の実装前に戻す

### 何を制御しているか

レビュー結果がその場限りで消えることを防ぐ。

### どうやって制御しているか

`claude-review-pdca` にレビュー指摘と学習済みパターンを保存する。  
次回実装時に、対象ファイルに関係するものだけ再注入する。

### どの水準で制御しているか

- 保存対象は再利用価値があるもの
- 低価値・一回限り・好みの問題は保存しすぎない
- 誤検知の却下は人間承認のみ
- プロジェクト単位で範囲を分け、別プロジェクトの指摘を混ぜない

### 説明例

```text
レビュー結果は、その場で消さず保存用データベースに保存します。
ただし、次回すべてをAIに読ませるのではなく、同じプロジェクト・同じファイル・重要度の高いものだけ戻します。
これにより、継続的に品質を上げつつ、ノイズでAIの判断を汚さないようにしています。
```

---

## 工程11. 繰り返し起きるものだけ、人間承認でルール化する

### 新しい単語

**ルール昇格** とは、保存用データベースに溜まった指摘や学習パターンのうち、再利用価値が高いものをプロジェクトルールにすること。

### 何を制御しているか

ルールを増やしすぎて、AIが読めない・守れない状態になることを防ぐ。

### どうやって制御しているか

ルール化の候補は出すが、書き込み前に人間承認を必須にする。

ルール化する条件:

- 今後も繰り返し使える
- 具体的でAIが実行できる
- 既存ルールと重複しない
- 一回限りの好みではない
- プロジェクト意図を変えない

### どの水準で制御しているか

- 自動で全プロジェクト共通ルールにしない
- プロジェクト内ルールを優先
- 差分を見せてから人間承認
- 重複や曖昧なルールは追加しない

### 説明例

```text
レビューで出た指摘をすべてルール化すると、ルールが肥大化して逆に守れなくなります。
そのため、まず保存用データベースに保存し、繰り返し起きるものや再利用価値が高いものだけを、人間承認つきでプロジェクトルールに昇格します。
```

## 面接官に伝える時の短いまとめ

```text
この仕組みでは、AI生成コードをそのまま信用せず、設計段階で確認ポイントを置いています。
実装前には過去の関連指摘を戻し、実装後は別文脈でレビューし、指摘を自動修正・人間確認・停止対象に分けます。
重大指摘は実際に起きるか確認してから直し、修正後は別文脈で再レビューします。
さらに、レビュー結果は保存し、次回実装前に対象ファイルへ関係するものだけ戻します。
これにより、AIコーディングを単発の自動化ではなく、継続的な品質管理プロセスとして扱っています。
```

## クライアント向けにさらに平易に言う場合

```text
AIに作業を任せると速い一方で、間違いに気づかないまま進むリスクがあります。
この仕組みでは、AIが作ったものを別のAIに確認させ、直してよいものだけ直し、判断が必要なものは人間に戻します。
また、過去に起きた失敗を次回の作業前に思い出させることで、同じ失敗を繰り返しにくくしています。
```

---

## この説明で避けるべき言い方

避ける:

- 「AIが全部自動で直します」
- 「レビューを何回も回すので安全です」
- 「Claude Codeを使い倒しています」
- 「問題が起きたので後から評価を足しました」

使う:

- 「自動化する範囲と人間判断に戻す範囲を先に分けています」
- 「重大指摘は実際に起きるか確認してから直します」
- 「レビュー結果を構造化して次の工程に使います」
- 「誤検知が増えたら止めます」
- 「過去の指摘を対象ファイルに限定して戻します」
