# クライアント・面接官向け: AIコードレビューの評価・ガードレール工程説明

この文書は、`review-fix-pipeline` と `claude-review-pdca` の仕組みを、クライアントや面接官に説明するための工程別説明である。

狙いは、専門用語を消して簡単に見せることではない。  
**必要な専門用語は出し、その場で意味・目的・事故防止上の役割を説明できる状態にする**ことである。

この文書で強調したいのは、単に「AIにレビューさせています」という話ではない。  
**AIが作ったものを、どの評価で確認し、どのガードレールで止め、どこから人間判断に戻すかを、作業前から設計している**という点である。

---

## まず前提: 評価とガードレールの意味

### 評価 / eval とは

この文書では、**評価 / eval（AIの出力やコード変更を次工程へ進めてよいか判定する仕組み）** を、点数付けだけの意味では使わない。  
AIが作ったコード、レビュー指摘、修正案を、次の工程へ進めてよいか確認するための仕組み全体として扱う。

具体的には、次の確認を含む。

- `lint`（コードの書き方や単純なミスを機械的に検査する仕組み）に通るか
- `unit test`（小さな機能単位の自動テスト）や確認コマンドで壊れていないか
- `diff`（変更差分。どのファイルのどの行を変えたか）が依頼範囲からはみ出していないか
- `review findings`（レビュー指摘。AIレビューで見つかった問題候補）が本当に修正対象か
- `severity`（重要度。影響の大きさを表す区分）が高い指摘を、根拠確認なしで直していないか
- 人間判断が必要な仕様・権限・セキュリティ判断を、AIが勝手に進めていないか
- 同じ失敗を繰り返していないか

### ガードレール / guardrail とは

**ガードレール / guardrail（AIが進めてよい範囲と止める条件を事前に決める安全境界）** は、AIを使わないための制限ではない。  
AIを安全に使うために、**どこまで自動化し、どこから人間に戻すかを事前に決める境界線**として扱う。

クライアント向けには、次のように説明する。

```text
AIに作業を任せる前に、自動で通してよい変更、確認が必要な変更、止めるべき操作を分けています。
AIの判断だけで危険な作業が進まないよう、lint、unit test、diff、review findings、HITL承認を通過条件にしています。
```

**HITL / Human-in-the-loop（人間を判断ループに入れること）** は、AIに任せきりにせず、仕様・セキュリティ・本番影響のような責任判断を人間確認に戻す設計を指す。

---

## 専門用語の扱い方針

専門用語は消しすぎない。  
ただし、初出時または重要箇所では、次の3点を一緒に説明する。

1. それが何か
2. 何を制御するために使うか
3. 事故前にどう止めるか

| 専門用語 | 説明時の補足 | この仕組みでの役割 |
|---|---|---|
| eval | AIの出力やコード変更を次工程へ進めてよいか判定する仕組み。 | AIの「大丈夫そう」という文章ではなく、確認条件で進行可否を決める。 |
| guardrail | AIが進めてよい範囲と止める条件を事前に決める安全境界。 | 自動化範囲、人間確認範囲、停止対象を分ける。 |
| lint | コードの書き方や単純ミスを機械的に検査する仕組み。 | 読み込み漏れ、未使用コード、単純な書き間違いを、AIの説明ではなく検査結果を正として止める。 |
| unit test | 小さな機能単位の自動テスト。 | 修正で既存機能を壊していないか確認する。 |
| CI | GitHub Actionsなどで、検査やテストを自動実行する仕組み。 | ローカルでは見落とした失敗を、マージ前に止める。 |
| diff | 変更差分。どのファイルのどの行を変えたか。 | 依頼範囲外の変更や大きすぎる変更を検知する。 |
| review findings | レビュー指摘。AIレビューで見つかった問題候補。 | 自動修正、人間確認、停止対象へ分類する材料にする。 |
| severity | 重要度。問題が本当に起きた場合の影響度。 | 高重要度の指摘を優先するが、AIの断定だけで即修正しない。 |
| false positive | 誤検知。実際には問題ではない指摘。 | 誤検知が増えたらレビュー反復を止め、不要な修正を防ぐ。 |
| HITL | Human-in-the-loop。人間を判断ループに入れること。 | 仕様・セキュリティ・本番影響など、責任判断を人間確認に戻す。 |
| observability | 何が起きたかをログ・結果・履歴から追える状態。 | レビュー結果、修正履歴、却下理由を後から説明できるようにする。 |
| rule promotion | ルール昇格。繰り返し使える指摘をプロジェクトルールにすること。 | 一回限りの指摘をルールにせず、再利用価値があるものだけ人間承認で昇格する。 |
| fresh reviewer | 新しい文脈のレビュー担当。実装理由を知らない状態で見るAI。 | 実装したAIの自己正当化や見落としを減らす。 |

## 全体像

この仕組みは、AIコーディングを次の流れで制御している。

```text
1. 作業前に、AIに任せる範囲を分ける
2. 実装前に、過去の失敗を作業文脈へ再注入する
3. AIが実装する
4. fresh reviewer（別文脈のAI）がレビューする
5. review findings（レビュー指摘）を、自動修正・HITL確認・停止対象に分ける
6. severity（重要度）が高い指摘は、再現確認してから直す
7. safe auto-fix（安全な自動修正）だけ適用する
8. 修正後に、別の文脈で再レビューする
9. false positive（誤検知）が増えたら止める
10. 結果を保存し、次回の実装前に必要な文脈として渡す
11. 繰り返し起きるものだけ、人間承認でrule promotion（ルール昇格）する
```

クライアント向けには、次の一言で説明できる。

> AIにコードを書かせるだけではなく、作業前・レビュー時・修正時・次回実装時に eval と guardrail を置き、危険な判断は HITL で人間に戻す品質管理フローです。

## 工程1. 作業前に、AIに任せる範囲を分ける

### 何を制御しているか

AIがどこまで関与してよいかを、作業前に分ける。  
重要なのは、「AIを使うか使わないか」ではなく、**どの判断を機械的な評価で通し、どの判断をAIに補助させ、どこをHITLで人間が決めるか**である。

### どうやって制御しているか

作業を4種類に分け、事故が起きる前に止まる場所を決める。

| 区分 | 判断主体 | AIが実際にやること | 事故前にどう制御するか | 確実性の根拠 |
|---|---|---|---|---|
| 機械的に確認できる作業 | `lint` / `unit test` / CI | プロジェクトで事前に決めた検査コマンド（例: コードの書き方検査、型チェック、単体テスト、ビルド、CI）を実行し、どのファイル・どのテスト・どの条件で失敗したかを要約する。 | 成功・失敗はAIの説明をそのまま受け取らず、コマンドの終了結果、テスト結果、CI結果を正として判定する。失敗していれば次工程へ進めない。 | プログラムの実行結果を正として判定するため、AIが「大丈夫そう」と説明しても成功扱いにならない。 |
| 小さく安全に直せる作業 | ルール + AI実装 + `diff`確認 | 読み込み漏れ、存在しない名前の参照、入力ミス、単純な条件漏れなどを小さい差分で直す。修正後は、変更した箇所に関係する検査コマンドや対象テストを再実行する。 | 修正対象、変更範囲、変更の種類を事前に限定する。対象外ファイルの変更、広すぎるdiff、検査・テスト失敗があれば止める。 | diffと検査結果で確認するため、AIが勝手に大きな設計変更を混ぜても完了扱いにしない。 |
| 判断が必要な変更 | HITL | 選択肢を2〜3案に整理し、影響範囲、移行コスト、確認すべき観点を説明する。推奨案は出してよい。 | 出力を「提案・比較・リスク・推奨」までに固定し、コード変更へ進めない。採用判断が必要な項目は人間確認待ちにする。 | 決定権を人間側に残すため、AIの提案がそのまま仕様変更として実装されない。 |
| 高リスク操作 | 人間承認またはブロック | 実行前に、対象、影響範囲、戻し方、必要な承認、代替案を説明する。可能ならdry-run（実変更なしの事前確認）までで止める。 | 秘密情報、外部送信、本番操作、破壊的削除、権限変更を事前にブロック対象として定義する。承認がなければ実行しない。 | 実行前ゲートで止めるため、事故が起きた後の検知ではなく、危険操作そのものを実行前に止められる。 |

### どの水準で制御しているか

- 検査対象は、作業前に決めた `lint`、型チェック、`unit test`、ビルド、CI、対象画面・対象APIの確認コマンドなどに基づく
- `lint` や `unit test` のように正誤が機械的に分かるものは、AIの説明をそのまま受け取らず、プログラムの実行結果を正として判定する
- 小さな修正は、対象ファイル・diff・検査結果で制御する
- 仕様・権限・セキュリティ・互換性の判断は、HITLで提案状態に止め、人間の決定なしに実装へ進めない
- 秘密情報・本番操作・破壊的操作は、事後検知ではなく実行前ゲートで止める

### 説明例

```text
この工程では、AIを使うかどうかではなく、事故前にどのゲートで止めるかを決めています。
lint、型チェック、unit test、ビルド、CIなど、事前に決めた確認方法に基づいて判断します。AIの説明をそのまま受け取らず、プログラムの実行結果を正として判定します。
AIには、検査コマンドの実行、失敗ログの要約、小さい修正、修正後の再確認までを任せます。
ただし、対象外ファイルの変更、広すぎるdiff、検査・テスト失敗があれば完了扱いにしません。
仕様やセキュリティのような責任判断は、HITLで人間確認に戻します。
```

## 工程2. 実装前に、過去の失敗を作業文脈へ再注入する

### 用語補足

**再注入 / reinjection（過去のレビュー指摘を、次回の実装前にAIの作業文脈へ渡すこと）** は、AIに過去の失敗を思い出させる仕組みである。  
この場合の「渡す」は、Claude Code の `/rewind` や Git の `restore` のように会話やコードを巻き戻すことではない。保存済みのレビュー指摘から、今回の編集に関係するものだけを取り出し、次の実装プロンプトや実装前コンテキストに入れるという意味である。  
ただし、すべてを渡すのではなく、今編集するファイルに関係するものだけを渡す。

### 何を制御しているか

AIが同じファイルで同じ種類の失敗を繰り返すことを防ぐ。  
これは、単なるメモではなく、**実装前のcontext injection（作業前に必要な文脈を渡すこと）** として扱う。

### Codexでの実操作

Codexの場合、再注入は `/rewind` のようなスラッシュコマンドではなく、次のように実装前コンテキストを作って渡す操作になる。

```powershell
python C:\Users\Tenormusica\claude-review-pdca\scripts\prepare-implementation-context.py `
  --session-id <作業ID> `
  --cwd <対象repo> `
  --file-path <編集対象ファイル> `
  --tool-name Edit
```

このスクリプトは、保存済みの `review findings` から対象ファイルに関係するものを絞り、Codexが実装前に読むべき注意点として出す。  
Codex側では、その出力をプロンプト、`CODEX.md` / `AGENTS.md`、または作業前メモとして渡す。  
一方で、実際にコード変更を元に戻す場合は reinjection ではなく、Git の `git restore <file>`、`git restore --staged <file>`、`git revert <commit>` などを使う。

### どうやって制御しているか

`claude-review-pdca` が、過去の `review findings` を保存用データベースに保存している。  
実装前に、対象ファイルに関係する指摘だけを取り出してAIに見せる。

取り出す条件は次のようなもの。

- 同じプロジェクトか
- 同じファイルか
- `severity` が十分高いか
- 古すぎないか
- すでに解決済みではないか
- 同じ作業中に重複して出していないか

### どの水準で制御しているか

- 全件を読ませない
- 対象ファイルに関係するものだけ
- 低優先度や古いものは除外
- 解決済みや人間が不要と判断したものは再注入しない

### 説明例

```text
レビュー指摘を一回で捨てず、次に同じファイルを触る前に関連する指摘だけをAIへ再注入しています。
これはコードや会話を巻き戻す操作ではなく、過去の指摘を次の実装前コンテキストとして渡す操作です。
全件を渡すとノイズになるので、プロジェクト、ファイル、severity、鮮度で絞ります。
これにより、AIが同じ失敗を繰り返しにくくしています。
```

## 工程3. AIが実装する

### 何を制御しているか

AIが作業範囲を広げすぎること、過去の注意点を忘れて実装することを制御する。

### どうやって制御しているか

実装時には、次の情報を前提に作業させる。

- 対象ファイル
- 再注入された `review findings`
- プロジェクトのルール（CLAUDE.md / AGENTS.md / CODEX.md など）
- 確認に使う `lint` / `unit test` / build コマンド
- 依頼された作業範囲

### どの水準で制御しているか

- 依頼範囲外の大規模な書き換えはしない
- 既存ルールと既存設計に合わせる
- 実装後に確認できる変更単位にする
- diff が広がりすぎた場合は、追加実装ではなく分割・確認に戻す

### 説明例

```text
実装工程では、AIに自由に作らせるのではなく、対象ファイル、過去のreview findings、プロジェクトルール、確認コマンドを渡してから作業させます。
これにより、AIがその場の推測で大きく設計を変えることを避けています。
```

## 工程4. fresh reviewer（別文脈のAI）がレビューする

### 用語補足

**fresh reviewer（実装理由を知らない新しい文脈のレビュー担当）** とは、実装したAIとは別の会話・別の状態でレビューさせることである。  
同じAIでも、実装理由を知っている状態で自己レビューさせると甘くなりやすいため、レビュー用に文脈を分ける。

**intent-first review / 意図優先レビュー（変更意図を先に推定してから、その意図に対する問題を探すレビュー）** とは、単に好みで指摘するのではなく、「この変更は何を達成したかったのか」を先に置いて確認する方法である。

### 何を制御しているか

AIが自分の実装を甘く見ること、または意図を無視して的外れなレビューをすることを制御する。

### どうやって制御しているか

`review-fix-pipeline` のレビュー工程では、まず変更意図を推定し、その意図の範囲で問題を出す。  
レビュー担当は実装担当とは別文脈にする。

### どの水準で制御しているか

- 実装とレビューを同じ文脈で閉じない
- 変更意図を推定してからレビューする
- 「好み」ではなく、意図に対するバグ・安全性・保守性の問題を出す
- 指摘は `review findings` として保存・分類できる形にする

### 説明例

```text
AIが自分で書いたコードを同じ会話でレビューすると、なぜそう書いたかを知っているため見落としが起きやすいです。
そのため、実装担当とレビュー担当をfresh reviewerとして分けています。
さらに、intent-first reviewで変更意図を推定し、その意図に対して本当に問題があるかを確認します。
```

## 工程5. review findingsを、自動修正・HITL確認・停止対象に分ける

### 用語補足

**auto-fixable / 自動修正候補（仕様判断なしで小さく直せる可能性がある指摘）** は、「AIが自信あり」という意味ではない。  
**意図を変えず、局所的に直せる** という意味で使う。

**judgment call / 人間判断項目（仕様・責任・方針の判断が必要な指摘）** は、AIが提案してよいが、勝手に実装してはいけない項目である。  
たとえば、API（外部から呼び出される入り口）の互換性、UX（画面の使い勝手）、セキュリティ方針、権限設計などが該当する。

### 何を制御しているか

AIが、責任ある設計判断まで勝手に直してしまうことを防ぐ。

### どうやって制御しているか

レビュー結果を次のように分ける。

| 分類 | 例 | 次の処理 |
|---|---|---|
| auto-fixable / 自動修正候補 | 明らかな参照ミス、読み込み漏れ、単純な条件漏れ、テスト期待値の明確なずれ | AIが小さく修正し、lint / unit test / 対象確認コマンドを再実行する |
| judgment call / 人間判断項目 | API互換性、UX変更、セキュリティ方針、権限設計、運用ルール変更 | AIは選択肢とリスクを説明し、HITLで人間確認へ戻す |
| stop / 停止対象 | 本番影響、データ削除、秘密情報、外部送信、破壊的操作 | ブロックまたは明示承認 |

### どの水準で制御しているか

- 自動修正は局所的で意図を変えないものに限定
- 仕様・権限・セキュリティ判断はHITLに戻す
- 高リスク操作はAI判断だけで進めない
- 分類理由を残し、後から「なぜ自動修正したか / なぜ止めたか」を説明できるようにする

### 説明例

```text
review findingsは、AIが直してよいものと、人間に戻すものを分けています。
auto-fixableは「AIが自信あり」ではなく、「仕様判断を含まず小さく直せる」という意味です。
API互換性、UX、セキュリティ方針のようなjudgment callは、AIが提案しても自動適用しません。
```

## 工程6. severityが高い指摘は、実際に起きるか確認してから直す

### 用語補足

**critical finding / 重大指摘（本当に起きるなら影響が大きいレビュー指摘）** は、優先して扱うべき指摘である。  
ただし、重大と言われたから必ず正しいわけではない。

**reproduction / 再現確認（小さなコードやテストで、指摘された問題が本当に起きるか確認すること）** は、AIの断定を実行結果で検証する工程である。

### 何を制御しているか

AIが「重大」と言った指摘をそのまま信じて、動いているコードを壊すことを防ぐ。

### どうやって制御しているか

`severity` が高い指摘は、修正前に最小限の再現確認を行う。  
たとえば、小さな確認コード、対象テスト、ログ確認を使って、本当に問題が起きるかを確認する。

### どの水準で制御しているか

- critical finding は即修正しない
- 実際に確認できるものは reproduction を取ってから直す
- 確認できないものは、HITLまたは追加調査に戻す
- 「重要度が高い」と「AIの指摘が正しい」を分けて扱う

### 説明例

```text
重大指摘ほど、そのまま直すと危険です。
AIがcritical findingだと言っても、まずreproductionを取り、本当に問題が起きるか確認します。
確認できたものだけ修正し、確認できないものはHITLに戻します。
```

## 工程7. safe auto-fix（安全な自動修正）だけ適用する

### 何を制御しているか

レビュー結果をもとに、AIが過剰修正やついで修正を行うことを防ぐ。

### どうやって制御しているか

修正担当は、auto-fixable に分類された指摘だけを修正する。  
judgment call や stop 対象は修正対象から外す。

### どの水準で制御しているか

- 修正対象は review findings に対応するものだけ
- 既存仕様を変えない
- 関係ない整理や作り替えを混ぜない
- 修正後に lint / unit test / 対象確認コマンドを行う
- diff が広がりすぎた場合は、自動修正を止めて人間確認に戻す

### 説明例

```text
修正工程では、review findingsのうちsafe auto-fixできるものだけを適用します。
ついでの整理や仕様変更は混ぜません。
修正後はlintやunit testを再実行し、diffが広がりすぎていないか確認します。
```

---

## 工程8. 修正後に、別の文脈で再レビューする

### 何を制御しているか

修正によって別の不具合が入ったり、最初のレビュー担当と同じ見落としが残ったりすることを防ぐ。

### どうやって制御しているか

修正後、別の新しい文脈の fresh reviewer で再レビューする。  
同じレビューの続きではなく、新しい状態で見直す。

### どの水準で制御しているか

- 再レビューは修正後の diff を対象にする
- review-fix loop（レビューして直し、再レビューする反復処理）には上限を置く
- 新しい auto-fixable が残っていれば再修正
- judgment call や stop 対象が出たらHITLへ回す

### 説明例

```text
修正後は、同じ文脈で「直りました」と判断せず、新しいfresh reviewerで再確認します。
これにより、修正による副作用や、最初のレビュー担当の見落としを拾いやすくしています。
ただし、review-fix loopは無限に回さず、上限と停止条件を置きます。
```

---

## 工程9. false positive（誤検知）が増えたら止める

### 用語補足

**false positive / 誤検知（実際には問題ではないのに、AIが問題として指摘したもの）** は、AIレビューで必ず発生しうるノイズである。

### 何を制御しているか

レビューを回しすぎて、AIが実問題ではなくノイズを直し始めることを防ぐ。

### どうやって制御しているか

レビューの反復が進むにつれて false positive が増えた場合、さらにレビューを続けず停止する。

### どの水準で制御しているか

- review-fix loop には上限を置く
- false positive の比率が高くなったら止める
- 「全部指摘が消えるまで回す」ことを目的にしない
- 誤検知として却下した理由を残し、次回の再注入対象から外す

### 説明例

```text
AIレビューは回せば回すほど良いわけではありません。
実際の問題を取り切った後は、false positiveが増えて、不要な修正で品質を下げることがあります。
そのため、誤検知が増えたら、追加レビューより停止を優先します。
```

---

## 工程10. 結果を保存し、次回の実装前に必要な文脈として渡す

### 何を制御しているか

レビュー結果がその場限りで消えることを防ぐ。  
同時に、不要な指摘まで次回に持ち越して、AIの判断を汚すことも防ぐ。

### どうやって制御しているか

`claude-review-pdca` に review findings、分類結果、修正結果、却下理由を保存する。  
次回実装時に、対象ファイルに関係するものだけを実装前コンテキストとして再注入する。

### どの水準で制御しているか

- 保存対象は再利用価値があるもの
- 低価値・一回限り・好みの問題は保存しすぎない
- false positive の却下は人間承認または明確な根拠つきで扱う
- プロジェクト単位で範囲を分け、別プロジェクトの指摘を混ぜない
- observability（後から何が起きたか追える状態）を残す

### 説明例

```text
レビュー結果は、その場で消さず保存用データベースに保存します。
ただし、次回すべてをAIに読ませるのではなく、同じプロジェクト・同じファイル・severityの高いものだけを実装前コンテキストとして渡します。
これにより、継続的に品質を上げつつ、ノイズでAIの判断を汚さないようにしています。
```

## 工程11. 繰り返し起きるものだけ、人間承認でrule promotionする

### 用語補足

**rule promotion / ルール昇格（再利用価値が高い指摘をプロジェクトルールにすること）** は、レビューで得た学習を次回以降の作業ルールに変える工程である。

### 何を制御しているか

ルールを増やしすぎて、AIが読めない・守れない状態になることを防ぐ。

### どうやって制御しているか

ルール化の候補は出すが、書き込み前にHITLで人間承認を必須にする。

ルール化する条件:

- 今後も繰り返し使える
- 具体的でAIが実行できる
- 既存ルールと重複しない
- 一回限りの好みではない
- プロジェクト意図を変えない

### どの水準で制御しているか

- 自動で全プロジェクト共通ルールにしない
- プロジェクト内ルールを優先
- diff を見せてから人間承認
- 重複や曖昧なルールは追加しない

### 説明例

```text
レビューで出た指摘をすべてrule promotionすると、ルールが肥大化して逆に守れなくなります。
そのため、まず保存用データベースに保存し、繰り返し起きるものや再利用価値が高いものだけを、HITL承認つきでプロジェクトルールに昇格します。
```

## 面接官に伝える時の短いまとめ

```text
この仕組みでは、AI生成コードをそのまま信用せず、設計段階でevalとguardrailを置いています。
実装前には過去のreview findingsを対象ファイルに絞って再注入し、実装後はfresh reviewerでintent-first reviewを行います。
出てきた指摘はauto-fixable、judgment call、stop対象に分類します。
severityが高いcritical findingは、reproductionを取って本当に起きるか確認してから直します。
修正後は別文脈で再レビューし、false positiveが増えたらreview-fix loopを止めます。
さらに、結果を保存して次回実装前の文脈として再注入し、繰り返し起きるものだけHITL承認でrule promotionします。
これにより、AIコーディングを単発の自動化ではなく、継続的な品質管理プロセスとして扱っています。
```
