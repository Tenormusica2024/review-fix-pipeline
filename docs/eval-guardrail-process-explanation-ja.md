# クライアント・面接官向け: AIコードレビューの評価・ガードレール工程説明

この文書は、`review-fix-pipeline` と `claude-review-pdca` の仕組みを、クライアントや面接官に説明するための工程別説明である。

前提として、ここでいう **評価（eval）** は「AIの出力を採点すること」だけではない。  
AIが出したコード変更や判断を、次の工程に進めてよいか確認するための評価基準・テスト・レビュー・記録をまとめて評価（eval）と呼ぶ。

ここでいう **ガードレール（AIに任せてよい範囲と、人間に戻す範囲を事前に決める安全設計）** は「AIを止める壁」ではなく、AIを安全に使うための判断境界である。


## 用語の置き換え方針

面接やクライアント説明では、内部実装寄りの英語をそのまま使わない。必要な場合だけ、次のように日本語を主にして括弧で補足する。

| 内部用語 | 説明時の言い方 |
|---|---|
| findings（レビュー指摘） | レビュー指摘（AIレビューで見つかった問題候補） |
| severity（重要度） | 重要度（指摘がどれくらい重大かを表す区分） |
| repo（リポジトリ） | リポジトリ（プロジェクトのコード一式） |
| DB（保存用データベース） | 保存用データベース（レビュー指摘を蓄積する台帳） |
| 自動修正候補（auto-fixable） | 自動修正候補（仕様判断なしで局所的に直せるもの） |
| 人間判断項目（judgment call） | 人間判断項目（仕様・責任・方針の判断が必要なもの） |
| critical finding（重大指摘） | 重大指摘（本当に起きるなら影響が大きい指摘） |
| false positive（誤検知） | 誤検知（実際には問題ではない指摘） |
| rule promotion（ルール昇格） | ルール昇格（繰り返し使える指摘をリポジトリ（repo）ルールへ上げること） |
| fresh reviewer（新しい文脈のレビュー担当） | 新しい文脈のレビュー担当（実装理由を知らない状態で見るAI） |
| loop（反復処理） | 反復処理（同じ流れを条件付きで繰り返すこと） |

---

## 全体像

この仕組みは、AIコーディングを次の流れで制御している。

```text
1. 作業前にリスクを分ける
2. 実装前に過去の失敗を戻す
3. AIが実装する
4. 別文脈のAIが意図を読んでレビューする
5. 指摘を自動修正可能 / 人間判断 / 高リスクに分類する
6. 重大指摘は実測してから直す
7. 安全な修正だけ適用する
8. 新しい文脈で再レビューする
9. ノイズが増えたら止める
10. 結果を保存用データベース（レビュー指摘を蓄積する台帳）に保存し、次回の実装前に戻す
11. 繰り返し起きるものだけ人間承認でルール化する
```

クライアント向けには、次の一言で説明できる。

> AIにコードを書かせるだけではなく、作業前・レビュー時・修正時・次回実装時に評価ポイントを置き、危険な判断は人間に戻す品質管理フローです。

## 工程1. 作業前にリスクを分ける

### 何を制御しているか

AIがどこまで関与してよいかを、作業前に分ける。  
ここで重要なのは、「AIを使うか使わないか」ではなく、**判断主体をどこに置くか**である。

### どうやって制御しているか

作業を4種類に分け、ルールベースで処理する範囲、AIに任せる範囲、人間に戻す範囲を明確にする。

| 区分 | 判断主体 | AIが実際にやること | 事故前にどう制御するか | 確実性の根拠 |
|---|---|---|---|---|
| 決定的チェック | ルールベース（テストや静的検査の結果で判断） | `pytest` や `npm test`、静的検査（lint: 文法・規約違反の検査）を実行し、失敗ログを要約する。 | 成否判定をAIの文章判断にしない。コマンドの終了コード、テスト件数、失敗ログをゲートにする。失敗していれば次工程へ進めない。 | 機械的な実行結果で判定するため、AIが「大丈夫そう」と言っても成功扱いにならない。 |
| 安全な修正 | ルールベース + AI実装 | import漏れ、未定義名エラー（NameError: 存在しない名前を参照した実行時エラー）、typo（入力ミス）、明確な条件漏れを小さい差分で直す。 | 修正対象ファイル、変更行数、変更種類を事前に限定する。修正後に `git diff` と関連テストを確認し、対象外ファイル変更・広範囲差分・テスト失敗があれば止める。 | 差分とテストで検知するため、AIが勝手に仕様変更や大規模リファクタを混ぜても、完了扱いにしない。 |
| 判断が必要な変更 | 人間。AIは選択肢整理とリスク説明まで | 選択肢を2〜3案に整理し、影響範囲、後方互換性、移行コスト、テスト観点を説明する。推奨案は出してよい。 | 出力形式を「提案・比較・リスク・推奨」までに固定し、コード変更へ進めない。採用判断が必要な項目には `人間確認待ち` の状態を付ける。 | 決定トークンが人間側に残るため、AIの提案がそのまま仕様変更として実装されない。 |
| 高リスク操作 | 人間承認またはブロック | 実行前に、対象、影響範囲、戻し方、必要な承認、代替案を説明する。可能ならdry-run（実変更なしの確認）や読み取り専用確認までに止める。 | 危険コマンド、秘密情報、外部送信、本番操作、破壊的削除、権限変更を事前にブロック対象として定義する。実行前に対象・影響・戻し方・承認有無を確認し、承認がなければ実行しない。 | 実行前ゲートで止めるため、事故が起きた後の検知ではなく、危険操作そのものを実行前に止められる。 |

### どの水準で制御しているか

- 正誤が機械的に判定できるものは、AIの文章ではなくコマンド結果で通すか止める
- 局所修正は、対象ファイル・差分・テスト結果で制御する
- 仕様・権限・セキュリティ・互換性の判断は、提案状態で止め、人間の決定なしに実装へ進めない
- 秘密情報・本番操作・破壊的操作は、事後検知ではなく実行前ゲートで止める

### 説明例

```text
この工程では、AIを使うかどうかではなく、事故前にどのゲートで止めるかを決めています。
テストや静的検査のように結果が明確なものは、AIの感想ではなくコマンド結果で判断します。
AIには、テスト実行、ログ要約、小さい修正、修正後の再検証までを任せます。
ただし、対象外ファイルの変更、広範囲差分、テスト失敗があれば完了扱いにしません。
呼び出し口の設計変更やセキュリティ方針のように責任判断が必要なものは、AIには選択肢整理とリスク説明までを任せ、決定は人間確認に戻します。
つまり、AIの速度は使いますが、通過条件はテスト・差分・承認状態のような確認可能なゲートで制御しています。
```

## 工程2. 実装前に過去の失敗を戻す

### 新しい単語

**再注入**: 過去のレビュー指摘を、次回の実装前にAIの作業文脈へ戻すこと。  
ただし全件を戻すのではなく、今編集するファイルに関係するものだけを戻す。

### 何を制御しているか

AIが同じファイルで同じ種類の失敗を繰り返すことを防ぐ。

### どうやって制御しているか

`claude-review-pdca` が、過去のレビュー指摘（AIレビューで見つかった問題候補）を保存用データベース（レビュー指摘を蓄積する台帳）に保存している。  
実装前に、対象ファイルに関係するレビュー指摘（AIレビューで見つかった問題候補）だけを取り出してAIに見せる。

絞り込み条件は次のようなもの。

- 同じリポジトリ（プロジェクトのコード一式）か
- 同じファイルか
- 重要度（severity: 指摘がどれくらい重大かを表す区分）が十分高いか
- 古すぎないか
- すでに解決済みではないか
- 同じセッションで重複注入していないか

### どの水準で制御しているか

- 全件注入しない
- 対象ファイルに関係するものだけ
- 低優先度や古いものは除外
- 解決済みや人間が不要と判断したものは再注入しない

### 説明例

```text
レビュー指摘を一回で捨てず、次に同じファイルを触る前に関連する指摘だけをAIへ戻しています。
全件を戻すとノイズになるので、リポジトリ（プロジェクトのコード一式）、ファイル、重要度（severity）、鮮度（古すぎないか）で絞ります。
これにより、AIが同じ失敗を繰り返しにくくしています。
```

## 工程3. AIが実装する

### 何を制御しているか

AIが作業範囲を広げすぎること、過去の注意点を忘れて実装することを制御する。

### どうやって制御しているか

実装時には、事前に戻されたレビュー指摘（findings）、リポジトリ（repo: プロジェクトのコード一式）のルール、対象ファイル、検証コマンドを前提に作業させる。

### どの水準で制御しているか

- 依頼範囲外の大規模rewriteはしない
- 既存ルールと既存設計に合わせる
- 実装後に検証できる変更単位にする

### 説明例

```text
実装工程では、AIに自由に作らせるのではなく、対象ファイル、過去の指摘、リポジトリ（repo）ルール、検証方法を渡してから作業させます。
これにより、AIがその場の推測で大きく設計を変えることを避けています。
```

## 工程4. 別文脈のAIが意図を読んでレビューする

### 新しい単語

**別文脈**: 実装したAIとは別の会話・別の状態でレビューさせること。  
同じAIでも、実装理由を知っている状態で自己レビューさせると甘くなりやすいため、レビュー用に文脈を分ける。

**Intent-first review**: 先に「この変更は何をしたかったのか」を推定してから、その意図に対して問題を探すレビュー方法。

### 何を制御しているか

AIが自分の実装を甘く見ること、または意図を無視して的外れなレビューをすることを制御する。

### どうやって制御しているか

`review-fix-pipeline` の `ifr` は、まず変更意図を推定し、その意図の範囲で問題を出す。  
レビュー担当は実装担当とは別文脈にする。

### どの水準で制御しているか

- 実装とレビューを同じ文脈で閉じない
- 変更意図を推定してからレビューする
- 「好み」ではなく、意図に対するバグ・安全性・保守性の問題を出す

### 説明例

```text
AIが自分で書いたコードを同じ会話でレビューすると、なぜそう書いたかを知っているため見落としが起きやすいです。
そのため、実装担当とレビュー担当を別文脈に分けています。
さらに、レビューでは最初に変更意図を推定し、その意図に対して本当に問題があるかを確認します。
```

## 工程5. 指摘を自動修正可能 / 人間判断 / 高リスクに分類する

### 新しい単語

**自動修正候補（auto-fixable）**: 仕様判断なしで局所的に直せる可能性がある指摘。  
ただし「AIが自信あり」という意味ではなく、仕様判断なしで局所的に直せるという意味。

**人間判断項目（judgment call）**: 人間の判断が必要な指摘。  
呼び出し口の設計（API設計）、利用体験（UX）、互換性、セキュリティ方針など、責任ある意思決定が必要なもの。

### 何を制御しているか

AIが、設計判断まで勝手に直してしまうことを防ぐ。

### どうやって制御しているか

レビュー結果を次のように分ける。

| 分類 | 例 | 次の処理 |
|---|---|---|
| 自動修正候補（auto-fixable） | 明確な参照ミス、import漏れ、局所的な条件漏れ | 自動修正候補 |
| 人間判断項目（judgment call） | 呼び出し口の仕様（API仕様）、画面仕様、セキュリティ方針 | 人間確認 |
| 高リスク項目（high-risk） | 本番影響、データ削除、秘密情報 | ブロックまたは明示承認 |

### どの水準で制御しているか

- 自動修正は局所的で意図を変えないものに限定
- 仕様・権限・セキュリティ判断は人間に戻す
- 高リスク操作はAI判断だけで進めない

### 説明例

```text
レビュー指摘は、AIが直してよいものと、人間に戻すものを分けています。
自動修正候補（auto-fixable）は「AIが自信あり」ではなく、「仕様判断を含まず局所的に直せる」という意味です。
呼び出し口の設計（API設計）やセキュリティ方針のような判断は、AIが提案しても自動適用しません。
```

## 工程6. 重大指摘は実測してから直す

### 新しい単語

**重大指摘（critical finding）**: 本当に起きるなら影響が大きいレビュー指摘。  
ただし、重大と言われたから必ず正しいわけではない。

**実測確認**: 実際に小さな再現コードやテストを動かして、指摘された問題が本当に起きるか確認すること。

### 何を制御しているか

AIが「重大」と言った指摘をそのまま信じて、動いているコードを壊すことを防ぐ。

### どうやって制御しているか

重大指摘（critical finding）は、修正前に最小再現で確認する。  
Pythonなら `python -c`、Nodeなら `node -e`、または小さなテストで実際に確認する。

### どの水準で制御しているか

- 重大指摘（critical finding）は即修正しない
- 実測できるものは実測してから直す
- 実測できないものは、人間判断または追加調査に戻す

### 説明例

```text
重大指摘ほど、そのまま直すと危険です。
AIが重大指摘（critical）と言っても、まず最小再現で本当に問題が起きるか確認します。
実測できたものだけ修正し、確認できないものは人間判断に戻します。
```

## 工程7. 安全な修正だけ適用する

### 何を制御しているか

レビュー結果をもとに、AIが過剰修正やついで修正を行うことを防ぐ。

### どうやって制御しているか

修正担当の作業文脈（main context）が自動修正候補（auto-fixable）だけを修正する。  
人間判断項目（judgment call）や高リスク操作（high-risk action）は修正対象から外す。

### どの水準で制御しているか

- 修正対象はレビュー指摘に対応するものだけ
- 既存仕様を変えない
- 関係ないリファクタを混ぜない
- 修正後にテストや簡易検証を行う

### 説明例

```text
修正工程では、レビューで見つかった問題のうち、安全に直せるものだけを適用します。
ついでのリファクタや仕様変更は混ぜません。
これにより、レビュー修正が新しい不具合を作るリスクを抑えています。
```

## 工程8. 新しい文脈で再レビューする

### 何を制御しているか

修正によって別のバグが入ったり、最初のレビュー担当と同じ見落としが残ったりすることを防ぐ。

### どうやって制御しているか

修正後、別の新しい文脈のレビュー担当（fresh reviewer）で再レビューする。  
同じ reviewer の続きではなく、新しい文脈で見直す。

### どの水準で制御しているか

- 再レビューは修正後の差分を対象にする
- 反復処理（loop）回数に上限を置く
- 新しい自動修正候補（auto-fixable）が残っていれば再修正
- そうでなければ完了または人間判断へ回す

### 説明例

```text
修正後は、同じ文脈で「直りました」と判断せず、新しいレビュー文脈で再確認します。
これにより、修正による副作用や、最初のレビュー担当の見落としを拾いやすくしています。
```

## 工程9. ノイズが増えたら止める

### 新しい単語

**誤検知（false positive）**: 実際には問題ではないのに、AIが問題として指摘したもの。  
日本語では「誤検知」と説明すると通じやすい。

### 何を制御しているか

レビューを回しすぎて、AIが実問題ではなくノイズを直し始めることを防ぐ。

### どうやって制御しているか

反復処理（loop）が進むにつれて誤検知（false positive）が増えた場合、さらにレビューを続けず停止する。

### どの水準で制御しているか

- レビュー回数には上限を置く
- 誤検知（false positive）比率が高くなったら止める
- 「全部指摘が消えるまで回す」ことを目的にしない

### 説明例

```text
AIレビューは回せば回すほど良いわけではありません。
実際の問題を取り切った後は、誤検知が増えて、不要な修正で品質を下げることがあります。
そのため、誤検知（false positive）が増えたら、追加レビューより停止を優先します。
```

## 工程10. 結果を保存用データベース（レビュー指摘を蓄積する台帳）に保存し、次回の実装前に戻す

### 何を制御しているか

レビュー結果がその場限りで消えることを防ぐ。

### どうやって制御しているか

`claude-review-pdca` にレビュー指摘（findings）と学習済みパターン（learned patterns: 過去に役立った修正・判断の型）を保存する。  
次回実装時に、対象ファイルに関係するものだけ再注入する。

### どの水準で制御しているか

- 保存対象は再利用価値があるもの
- 低価値・一回限り・好みの問題は保存しすぎない
- 誤検知のdismissは人間承認のみ
- リポジトリ（repo）単位でスコープを分け、別プロジェクトの指摘を混ぜない

### 説明例

```text
レビュー結果は、その場で消さず保存用データベース（DB）に保存します。
ただし、次回すべてをAIに読ませるのではなく、同じリポジトリ（repo）・同じファイル・重要度の高いものだけ戻します。
これにより、継続的に品質を上げつつ、ノイズでAIの判断を汚さないようにしています。
```

## 工程11. 繰り返し起きるものだけ人間承認でルール化する

### 新しい単語

**ルール昇格（rule promotion）**: 保存用データベース（DB）に溜まった指摘や学習パターンのうち、再利用価値が高いものを `CLAUDE.md` や `CODEX.md` のようなリポジトリ（repo）ルールに昇格すること。

### 何を制御しているか

ルールを増やしすぎて、AIが読めない・守れない状態になることを防ぐ。

### どうやって制御しているか

ルール化の候補は出すが、書き込み前に人間承認を必須にする。

ルール化する条件:

- 今後も繰り返し使える
- 具体的でAIが実行できる
- 既存ルールと重複しない
- 一回限りの好みではない
- プロジェクト意図を変えない

### どの水準で制御しているか

- 自動でglobal ruleにしない
- リポジトリ内ルール（repo-local rule）を優先
- 差分を見せてから人間承認
- 重複や曖昧なルールは追加しない

### 説明例

```text
レビューで出た指摘をすべてルール化すると、ルールが肥大化して逆に守れなくなります。
そのため、まず保存用データベース（DB）に保存し、繰り返し起きるものや再利用価値が高いものだけを、人間承認つきでリポジトリ（repo）ルールに昇格します。
```

## 面接官に伝える時の短いまとめ

```text
この仕組みでは、AI生成コードをそのまま信用せず、設計段階で評価ポイントを置いています。
実装前には過去の関連指摘を戻し、実装後は別文脈でレビューし、指摘を自動修正可能・人間判断・高リスクに分けます。
重大指摘は実測してから直し、修正後は別文脈で再レビューします。
さらに、レビュー結果は保存用データベース（DB）に保存し、次回実装前に対象ファイルへ関係するものだけ戻します。
これにより、AIコーディングを単発の自動化ではなく、継続的な品質管理プロセスとして扱っています。
```

## クライアント向けにさらに平易に言う場合

```text
AIに作業を任せると速い一方で、間違いに気づかないまま進むリスクがあります。
この仕組みでは、AIが作ったものを別のAIに確認させ、直してよいものだけ直し、判断が必要なものは人間に戻します。
また、過去に起きた失敗を次回の作業前に思い出させることで、同じ失敗を繰り返しにくくしています。
```

## この説明で避けるべき言い方

避ける:

- 「AIが全部自動で直します」
- 「レビューを何回も回すので安全です」
- 「Claude Codeを使い倒しています」
- 「問題が起きたので後から評価（eval: AI出力を次工程に進めてよいか確認する基準・テスト・レビュー）を足しました」

使う:

- 「自動化する範囲と人間判断に戻す範囲を先に分けています」
- 「重大指摘は実測してから直します」
- 「レビュー結果を構造化して次の工程に使います」
- 「誤検知が増えたら止めます」
- 「過去の指摘を対象ファイルに限定して戻します」
