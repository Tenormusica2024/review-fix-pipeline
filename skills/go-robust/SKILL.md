# go-robust — レビュー要確認の一括処理

レビュースキル（`/rfl`, `/ifr`, `/review-fix-loop` 等）が「要確認」を出したとき、以下の方針を適用して全件処理する。

## 適用方針

以下の5原則を適用する。この方針で解釈可能なものはすべて確定し、それでもなお判断できない場合のみ要確認として残す。

1. **堅牢性・保守性・安定性を最優先** — 実装コストの増加は許容する
2. **不確実性は安全側に倒す** — 迷ったら保守的な仮定を置き、より堅牢な方を選ぶ
3. **サイレントな問題を残さない** — 前提逸脱・失敗は必ず検知可能な形で扱う（例外・ログ・assertion 等）
4. **必要十分な対応にとどめる** — 冗長な推論・不要な出力・過剰な処理は避ける
5. **AIエージェント可読性 / 長期保守性を最優先** — 長期的に使われるプロジェクトでは、半年後のフレッシュセッションAIが迷わず改修できる構造を保つ（詳細は下記）

## 原則 5 の詳細: AIエージェント可読性 / 長期保守性

**適用対象:** 長期保守を前提とする主要プロジェクト。短期スクリプト・実験コードは対象外。

**判定基準:** フレッシュセッションのAIエージェント（文脈なし）がファイル単体を読んで、責務・データフロー・非自明な意思決定を即座に理解できるか。

**処理する（確定）:**
- 巨大関数の単一責任分割（100行超・複数責務入り）
- 似ているが意味が違う名前の統一（アクション名・状態コード）
- サイレント失敗の検知可能化（`except Exception: pass` → ログ + raise）
- 同じ処理の散在を共通ヘルパーに集約（3箇所目の出現で DRY 化）
- 深いネスト（5段以上）の早期 return / ガード節化
- 未使用コード・後方互換の残骸削除
- 型注釈の補完（暗黙の `dict | None` 等）
- 特殊ケース用の分岐が本流に混ざる場合の分離

**要確認として残す:**
- 責務分離の境界が複数案あり、どこで切るかが設計判断になる場合
- 共通ヘルパー化にあたって API を破壊的変更する必要がある場合
- 原子性保証などアーキテクチャレベルの方式選定（`O_EXCL` vs `mkdir` vs `filelock` 等）

## 実行手順

### Step 0: 要確認の有無チェック（早期終了）

**このステップを最初に実行し、要確認が0件なら即終了する。**

**取得元の優先順序:** 会話履歴に要確認セクションが存在する場合はそちらを正とする。存在しない場合のみ `review-feedback.db` を参照する。

- 直近のレビュー出力の「要確認」セクションを参照 → 件数をカウント
- 会話履歴に要確認セクションがない場合のみ `review-feedback.db` を確認:
  ```bash
  python "$HOME/.claude/scripts/review-feedback.py" query --resolution pending
  ```

**判定:**
- 要確認が **0件** → 「要確認なし。対応不要。」と報告して終了（Step 1〜4 はスキップ）
- 要確認が **1件以上** → Step 1 へ進む

### Step 1: 要確認項目の収集

Step 0 と同じ優先順序（会話履歴優先・なければ db）で要確認を把握する。

### Step 2: 方針による分類

各要確認に対し4原則を適用して分類する:

| 判断 | 基準 | 対応 |
|------|------|------|
| **処理可能** | 方針から答えが一意に定まる / 不確実性があっても安全側を選べる | 即実装・修正を実行 |
| **判断不能** | 仕様・要件・ビジネス判断が必要で方針では決定できない | 要確認として残す |

**「実害なし」は要確認の理由にならない:**
「現状では実害が出ていない」という理由だけで判断不能に分類しない。4原則で解釈可能なら処理可能として扱う。要確認にするのは、対処することで別のリスクが生じる、または明確なトレードオフが存在する場合のみ。

**各原則の判断基準:**

| 原則 | 処理する（確定） | 要確認として残す |
|------|----------------|----------------|
| 堅牢性優先 | エラーハンドリング追加・強化、try/finally・リソース解放、バリデーション強化 | アーキテクチャ大規模変更、要件不明な仕様変更 |
| 安全側に倒す | 型チェック・境界値チェック追加、デフォルト値を安全な値に変更 | A/B 両案が方針的に同等で要件に依存する選択 |
| 検知可能にする | サイレント例外をログ・raise に変更、assert/guard 追加、エラーコードを明示化 | 検知方法がシステム設計全体に影響する変更 |
| 必要十分 | 重複コード・デッドコード削除、不要な複雑性の排除 | スコープ不明の削除・リファクタリング |
| AIエージェント可読性 | 巨大関数の単一責任分割、命名統一、深いネスト浅化、型注釈補完、同処理の共通化 | 責務分離の切り方が複数案ある、API破壊的変更を伴う共通化、アーキテクチャレベルの方式選定 |

### Step 3: 実装実行

処理可能と判断したものを順次実装・修正する。
`/qc` 相当の静的チェック・テストを実施してから完了とする。

### Step 4: 完了報告

- 処理した件数 / 残った要確認件数
- 残った要確認は「なぜ判断できないか」を1行で説明

### Step 5: コミット・プッシュ（分岐）

**スキップ条件（以下のいずれかに該当する場合はスキップ）:**
- Step 0 早期終了（そもそも要確認 0件）
- Step 3 の実行件数が 0件（処理可能な要確認が存在しなかった）

上記以外（Step 3 で1件以上修正した場合）のみ、このステップを実行する。

**分岐条件は「Step 2 で判断不能に分類された件数」:**

**判断不能 0件の場合（処理可能なものをすべて修正済み）:**
`/commit` を即実行してプッシュまで完了する。

**判断不能 1件以上の場合:**
まず判断不能の要確認を一覧提示してユーザーの返答を待つ。ここで一旦停止する。

ユーザーが各件にコメントを返したら:
- **「修正してほしい + 方針」の場合**: そのコメントを判断根拠として4原則の枠内で修正を実行する
- **「今回は対処しない / スキップ」の場合**: その件は修正しない（スキップとして記録する）

全件のコメントを受け取り、修正対象の実装が完了したら `/commit` を実行してプッシュまで完了する。
「今回は対処しない」件が残っていても `/commit` は走らせる。
